Every request to the Google API must be authenticated. Google supports two authentication methods: API keys for server-to-server integrations and OAuth 2.0 for user-facing applications where you need to act on behalf of individual users. Both methods use the `Authorization` header with a Bearer token — the difference lies in how you obtain that token and what level of access it grants.

<Warning>
  Never hardcode API keys or tokens directly in your source code. Use environment variables or a secrets manager to keep credentials out of version control.
</Warning>

## API Keys

API keys are the simplest way to authenticate. You can generate one from your Google dashboard under **Settings → API Keys**. Pass the key in the `Authorization` header on every request using the Bearer scheme.

```text
Authorization: Bearer <api_key>
```

Live keys are prefixed with `ggl_live_` and test keys with `ggl_test_`. Use test keys during development to avoid affecting production data.

<CodeGroup>
  ```bash cURL
  curl -X GET https://api.google.com/v1/accounts \
    -H "Authorization: Bearer ggl_live_xxxxxxxxxxxx"
  ```

  ```javascript JavaScript
  const response = await fetch('https://api.google.com/v1/accounts', {
    headers: {
      'Authorization': 'Bearer ggl_live_xxxxxxxxxxxx',
      'Content-Type': 'application/json'
    }
  });
  const data = await response.json();
  ```

  ```python Python
  import requests

  headers = {
      'Authorization': 'Bearer ggl_live_xxxxxxxxxxxx',
      'Content-Type': 'application/json'
  }
  response = requests.get('https://api.google.com/v1/accounts', headers=headers)
  data = response.json()
  ```
</CodeGroup>

## OAuth 2.0

Use OAuth 2.0 when your application needs to access the API on behalf of an end user rather than your own account. OAuth is the right choice for multi-tenant applications, user-facing dashboards, and any scenario where users grant your app permission to interact with their Google data.

**When to use OAuth instead of API keys:**
- Your app acts on behalf of multiple users
- You need scoped, revocable access per user
- You're building a public-facing integration

To obtain an OAuth 2.0 access token, redirect users to the Google authorization endpoint and exchange the returned authorization code for a token:

```bash
curl -X POST https://api.google.com/v1/oauth/token \
  -H "Content-Type: application/json" \
  -d '{
    "grant_type": "authorization_code",
    "code": "AUTH_CODE_FROM_REDIRECT",
    "client_id": "your_client_id",
    "client_secret": "your_client_secret",
    "redirect_uri": "https://yourapp.com/callback"
  }'
```

```json
{
  "access_token": "eyJhbGciOiJSUzI1NiIsInR5cCI6IkpXVCJ9...",
  "token_type": "Bearer",
  "expires_in": 3600,
  "refresh_token": "ggl_refresh_xxxxxxxxxxxx"
}
```

Use the returned `access_token` as the Bearer token in all subsequent requests. Access tokens expire after the `expires_in` period (in seconds); use the `refresh_token` to obtain a new one without requiring the user to re-authorize.

## Authentication Errors

If authentication fails, the API returns a `401` or `403` response. Use the `error.code` field to determine the cause and take the appropriate action.

| HTTP Status | Error Code | Description |
|-------------|------------|-------------|
| `401` | `unauthorized` | The `Authorization` header is missing or the token is invalid |
| `401` | `token_expired` | The access token has expired — refresh it and retry |
| `403` | `forbidden` | The token is valid but lacks permission to access this resource |
| `403` | `scope_insufficient` | The OAuth scope does not include the required permission |
| `401` | `token_revoked` | The token has been manually revoked by the user or admin |
